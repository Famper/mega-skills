# Фикс блокеров PR → пуш → зелёный CI → вердикт

Аргументы: `$ARGUMENTS` — номер PR, опционально слово `security` — работать только по блокерам безопасности.

## 1. Когда этот скилл применим

Скилл меняет чужую ветку, поэтому запускается только по явной просьбе пользователя исправить код: «исправь блокеры», «почини и запушь», «доведи до зелёного CI», «fix и пуш».

- Просьба звучит как «проверь», «посмотри», «отревьюй», «дай вердикт» — правок не просили. Работать по скиллу `security-review` (только чтение), отдать отчёт и спросить, исправлять ли блокеры. Не коммитить и не пушить.
- Непонятно, просили правки или нет — считать, что не просили, и спросить.
- Автор PR — другой человек: перед **первым** пушем сказать, что именно уйдёт в его ветку (файлы и суть фиксов). Если пользователь уже сказал «исправь и запушь» — это и есть подтверждение, спрашивать второй раз не нужно.
- Исправлять только блокеры, если пользователь не просил иного. Находки уровней ВАЖНО и МЕЛОЧЬ идут в отчёт, а не в коммиты.

## 2. Подготовка

- `gh pr view <PR>` и `gh pr diff <PR>`: цель PR и объём изменений.
- Вычекать ветку PR в отдельный git worktree, не трогая текущую рабочую копию.
- Перед тестами выполнить проверки из скилла `preflight` (Docker, APP_URL, изоляция БД).

## 3. Ревью

Ревью делается по скиллу `security-review`: его чек-лист общего ревью (корректность, производительность, обработка ошибок, качество тестов, совместимость миграций и API, контракт с парным PR), чек-лист безопасности, градация важности (БЛОКЕР / ВАЖНО / МЕЛОЧЬ), обязательный сценарий у каждой находки, отделение проблем этого PR от старых и формат отчёта.

**Объём.** Просьба «отревьюй PR и security» — это ОБА ревью: общее ревью кода И проверку безопасности. Одно не подменяет другое; в отчёте это два отдельных подписанных раздела. Слово `security` без просьбы об общем ревью — только безопасность.

Если в PR уже есть опубликованное ревью с блоком состояния (`mega-skills-review`), работать инкрементально по пункту 1 того скилла: новый диф плюс перепроверка открытых находок, а не всё заново.

## 4. Исправление

- К каждому исправлению — регрессионный тест. Показать, что тест **падает** на старом коде и **проходит** на новом.
- Изменения минимальные, без попутного рефакторинга и без правок находок уровня МЕЛОЧЬ.
- Перед пушем: полный прогон тестов, PHPStan и phpcs для PHP, `npm run build` (бюджет бандла) для фронтенда.
- Проверка на свежем main делается **локально и не пушится**: в отдельном worktree `git merge origin/main`, прогон тестов (ловит конфликты миграций и тесты с хардкодом общих конфигов — например списков директив CSP), результат мержа выбросить.

## 5. Пуш

Ветка PR — чужая опубликованная история: её нельзя перезаписывать. Никогда не делать force-push, не перебазировать ветку PR на main, не менять уже запушенные коммиты (`amend`, `rebase -i`) и не мержить PR самому.

- `git fetch` и проверить, не запушил ли уже автор или другая сессия. Если запушили — забрать их коммиты, перепроверить, что фикс всё ещё нужен, и класть свои поверх.
- Свои **ещё не запушенные** коммиты можно подтянуть к свежей голове ветки: `git fetch origin && git rebase origin/<ветка PR>`. Это переписывает только свои локальные коммиты, push после этого обычный, без `--force`.
- `git push origin HEAD:<ветка PR>` — обычный push. Если push отклонён как non-fast-forward, значит в ветку запушили: вернуться к первому пункту. `--force` не добавлять ни при каких условиях.
- Если ветка отстала от main настолько, что тесты падают только из-за этого, — это не работа ревьюера: написать в отчёте и попросить автора обновить ветку. Обновить самому (мерж main в ветку PR — он пушится без force, в отличие от rebase) только по явной просьбе пользователя.

## 6. CI

- `gh pr checks <PR> --watch`. Если джоба упала: `gh run view <run-id> --log-failed`, исправить, запушить, повторить (до 3 итераций).
- Не выносить финальный вердикт, пока CI не завершён. Если ждать нельзя — явно написать, что CI не подтверждён.

## 7. Вердикт и запись в PR

Отчёт — по формату из пункта 8 скилла `security-review`, плюс строки про сделанные правки:

```
Вердикт: МЕРЖИТЬ | МЕРЖИТЬ ПОСЛЕ <PR или условие> | НЕ МЕРЖИТЬ
Исправлено: <блокеры с номерами находок и SHA коммитов>
Осталось: Важно — <номера и сроки>; Мелочи — <номера>
Проверено: <тесты и прогоны, которые реально выполнены>
Не проверено: <что осталось без проверки>
CI: зелёный | упал на <джоба> | не дождался
Порядок деплоя: <если зависит от других PR: backend → gateway → frontend>
```

Вердикт «МЕРЖИТЬ» без заполненных строк «Проверено» и «Не проверено» не выносить.

Отчёт выложить в PR по пункту 9 скилла `security-review` — комментарий с блоком состояния и построчные комментарии к находкам. Публикация в PR спрашивается отдельно: разрешение исправить и запушить код не распространяется на комментарии от имени пользователя. Исправленные блокеры в блоке состояния помечаются закрытыми с SHA коммита, чтобы следующее ревью их не искало заново.
