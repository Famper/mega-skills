# Ревью PR: общее + безопасность (только чтение)

Аргументы: `$ARGUMENTS` — номер PR, опционально слово `security` — только раздел безопасности.

Скилл **только читает и проверяет**: ничего не коммитить и не пушить в ветку PR. Исправить блокеры, запушить и дождаться CI — это скилл `review-pr`, и только по явной просьбе пользователя менять код.

Публикация отчёта в PR (комментарий, комментарии к строкам) — действие наружу: спросить разрешение и запостить только после «да».

## 1. Контекст PR и прошлое ревью

- `gh pr view $ARGUMENTS --json title,body,files,headRefName,headRefOid,author` — цель PR, изменённые файлы, ветка, SHA головы, автор.
- `gh pr checks $ARGUMENTS` — текущий статус CI.
- Найти своё прошлое ревью этого PR:
  `gh api repos/{owner}/{repo}/issues/$ARGUMENTS/comments --jq '.[] | select(.body | contains("mega-skills-review")) | {id, body}'`.
  В таком комментарии есть блок состояния из пункта 8: SHA проверенного коммита и номера открытых находок.
- Дальше три случая:
  - **Прошлого ревью нет** — полное ревью: `gh pr diff $ARGUMENTS`.
  - **Есть, и SHA совпадает с головой ветки** — нового кода нет. Не гонять всё заново: вернуть прошлый отчёт, сказать, что ветка не менялась, и перечислить открытые находки.
  - **Есть, но SHA другой** — инкрементальное ревью:
    - ревьюить только новое: `git diff <проверенный SHA>..<SHA головы>`;
    - перепроверить каждую открытую находку прошлого отчёта и поставить ей статус: закрыта / открыта / оказалась неверной;
    - если в новом дифе есть миграция, общий конфиг или модуль, от которого зависят другие места, — смотреть эти места целиком: по дифу такие поломки не видны;
    - тесты: только затронутые изменением плюс те, что падали в прошлый раз. Полный прогон (пункты 2–3) и ожидание CI — только перед вердиктом «МЕРЖИТЬ».
- Если PR парный (бэкенд ↔ gateway ↔ фронтенд), найти соседний PR: он нужен в пункте 5.

## 2. Изолированный worktree и тесты

- Создать временный worktree на ветку PR, не трогая текущую рабочую копию:
  `git fetch origin && git worktree add <путь-в-temp> origin/<ветка-PR>`.
- Скопировать `.env` из основного checkout и убедиться, что `APP_KEY` задан (без него Laravel падает на старте). Если ключа нет — `php artisan key:generate`.
- Valkey/Redis требует пароль: взять из `.env`, при необходимости поднять одноразовый контейнер.
- Остальное окружение — по скиллу `preflight` (Docker/OrbStack, `APP_URL`, изоляция тестовой БД, смонтированный worktree).
- Прогнать тесты в Docker, а не на хосте: тулчейн на хосте падает (tsx TransformError, отсутствие нативного lightningcss). Запускать внутри контейнера web/app или через `bin/test-worktree.sh`, если он есть в репозитории.
- Для превью в браузере поднимать свой dev-сервер на свободном порту. Никогда не использовать сервер другого worktree.

## 3. Прогон на свежем main

- В том же временном worktree влить свежий main локально: `git fetch origin && git merge origin/main` (не пушить результат).
- Перезапустить тесты — это ловит расхождения, которых не видно ни в ветке PR, ни в CI: конфликты миграций, изменившиеся общие конфиги, тесты с хардкодом общих списков (например директив CSP).
- Отдельно отметить в отчёте: тест упал только после мержа main или падал и до него.

## 4. Чек-лист общего ревью

Проходить по всем пунктам, по возможности параллельно отдельными субагентами. Пункт, который к этому PR не относится (нет миграций, нет публичного API), помечается в отчёте как неприменимый, а не молча опускается.

- **Корректность** — граничные случаи: дубли строк, дедлоки и транзакции, unix-time против DATE, часовые пояса (Москва), пустые и null значения, деление на ноль, округление денег, повторный вызов (идемпотентность), гонки при параллельных запросах.
- **Производительность** — запрос в цикле (N+1) и ленивая загрузка связей в цикле; новый фильтр, сортировка или join без индекса; выборка без лимита и пагинации; загрузка всей таблицы или всего ответа в память; тяжёлая работа синхронно в запросе вместо очереди; внешний вызов внутри цикла; кеш без инвалидации или с ключом без учёта пользователя/организации.
- **Обработка ошибок** — проглоченные исключения (пустой `catch`, `catch → return null`, `?.` вместо проверки); внешний вызов без таймаута и без разумного ретрая; потеря контекста при повторном выбросе; частичная запись без транзакции или компенсации; ошибка, которую пользователь видит как успех; в логах либо секреты и персональные данные, либо вообще ничего.
- **Качество тестов** — тест действительно падает без фикса (проверить: откатить фикс, убедиться, что тест красный); проверяются утверждения, а не только отсутствие исключения; нет заведомо зелёных проверок (`assertTrue(true)`, мок, который возвращает ровно ожидаемое, snapshot без просмотра); покрыт краевой случай из бага, а не только happy path; тест не зависит от порядка выполнения, текущего времени и сети; фикстуры не оставляют мусор следующим тестам.
- **Обратная совместимость миграций** — миграция применима на работающем старом коде (expand/contract: сначала добавить, потом переключить код, удалять в следующем релизе); нет переименования или удаления колонки и таблицы, которые читает текущий прод; нет `NOT NULL` без `DEFAULT` на непустой таблице; нет блокирующей операции на большой таблице (`ALTER`, индекс без `CONCURRENTLY`); есть откат; бэкфил данных порциями, а не одним `UPDATE`; порядок «миграция → деплой кода» выдержан.
- **Обратная совместимость API** — убранное или переименованное поле ответа; сузившийся тип или набор значений; новое обязательное поле запроса; изменившийся код ошибки или HTTP-статус; изменившийся формат (дата, число, пагинация); изменившееся поведение по умолчанию. Старые клиенты (фронтенд, мобильное приложение, интеграторы) должны продолжать работать, иначе нужна версия или период совместимости.
- **Контракт с парным PR** — маршруты, поля запросов и ответов, коды ошибок и требования к авторизации совпадают с соседним репозиторием. Эндпоинт, который вызывает фронтенд, должен существовать в main или в открытом PR бэкенда — и с теми же правами доступа.
- **Порядок деплоя** — если PR требует соседних: backend → gateway → frontend, и выкатка в другом порядке ничего не ломает.

## 5. Чек-лист безопасности

- **authz / IDOR** — на каждом новом или изменённом эндпоинте: проверка прав есть, объект привязан к текущему пользователю или организации, id из запроса не используется для доступа напрямую.
- **XSS** — вывод пользовательских данных без экранирования, `v-html`/`dangerouslySetInnerHTML`, рендер HTML из БД, атрибуты и `href` из пользовательского ввода.
- **Open redirect** — редиректы по параметру из запроса (`?next=`, `?return_url=`): адрес должен проверяться по белому списку, а не только на префикс.
- **Утечка сессии и личности при входе/выходе** — регенерация сессии после логина и смены пароля, полное уничтожение сессии при логауте, отсутствие остатков предыдущего пользователя в кеше, очередях и логах, корректность флагов cookie (`HttpOnly`, `Secure`, `SameSite`).
- **Rate limits** — есть ли лимит на новых публичных и аутентификационных эндпоинтах. За Next.js бэкенд видит только IP сервера Next.js, поэтому лимит должен считаться по проброшенному IP клиента, иначе он либо общий на всех, либо не работает вовсе.
- Попутно: секреты и пароли в логах, CSV formula injection, SQL-инъекции в сырых запросах, загрузка файлов без проверки типа и размера, SSRF в запросах по пользовательскому URL.

Если просили «ревью и security» — делать **оба** раздела, общее ревью не заменяется проверкой безопасности.

## 6. Градация важности

У каждой находки ровно один уровень:

- **БЛОКЕР** — мержить нельзя. Баг, который увидит пользователь или прод, уязвимость, потеря или порча данных, сломанный контракт, миграция, несовместимая с текущим кодом.
- **ВАЖНО** — мержить можно, исправить обязательно, со сроком: «до релиза» или «следующим PR». Неверный результат в краевом случае, проглоченная ошибка, N+1 на горячем пути, тест, который не может упасть, несовместимое изменение API без версии, отсутствие лимита на непубличном эндпоинте.
- **МЕЛОЧЬ** — на усмотрение автора: имена, стиль, структура, рефакторинг, дубли без последствий.

Сомнение между уровнями решается вопросом «что будет, если это не исправить»: увидит пользователь или прод — БЛОКЕР; не увидит, но код даёт неверный результат или скрывает ошибку — ВАЖНО; не меняет поведение — МЕЛОЧЬ.

## 7. Что попадает в отчёт

**Сценарий обязателен** для каждого БЛОКЕРА и каждого ВАЖНО: конкретный вход или состояние → что произойдёт. Нет сценария — находки нет: либо проверить (тестом, запросом, чтением кода) и дописать сценарий, либо выбросить. Догадки, «возможно сломается», «стоит проверить на всякий случай» в отчёт не идут. Если проверить не получилось, а риск серьёзный — это не находка, а отдельная строка «Не проверено» в отчёте. МЕЛОЧИ — одной строкой, без сценария.

**Только то, что принёс этот PR.** Находка идёт в основной отчёт, если она в строках дифа или в поведении, которое PR изменил. Проверять по дифу (`gh pr diff`, `git diff origin/main...<ветка PR>`), спорную строку — через `git log -L <начало>,<конец>:<файл>` или `git blame`. Старые проблемы, которых PR не касался, — отдельный короткий раздел «Было до PR»: только блокеры и уязвимости, не больше трёх, без требования исправить их в этом PR. Остальное старое молча опустить.

## 8. Отчёт на русском

Находки нумерованные, у каждой файл и строка. Нумерация сквозная и сохраняется между повторными ревью: закрытая находка остаётся под своим номером с пометкой «закрыта в <SHA>».

```
Ревью PR <номер> — <SHA головы>, диф <полный | SHA..SHA>

Блокеры
1. <файл:строка> — <что сломано>
   Сценарий: <вход или состояние> → <что произойдёт>

Важно (исправить до <релиза | следующего PR>)
2. <файл:строка> — <что не так>
   Сценарий: <вход или состояние> → <что произойдёт>

Мелочи
3. <файл:строка> — <стиль, имена, рефакторинг>

Было до PR (этот PR не трогал, в этом PR можно не исправлять)
- <файл:строка> — <блокер или уязвимость, не больше трёх строк>

Безопасность
authz/IDOR    — OK | неприменимо | <номер находки>
XSS           — OK | неприменимо | <номер находки>
Open redirect — OK | неприменимо | <номер находки>
Сессии/логин  — OK | неприменимо | <номер находки>
Rate limits   — OK | неприменимо | <номер находки>
Контракт      — OK | неприменимо | <номер находки>

Проверено
<какие тесты прогонялись и где (Docker, какие наборы); прогон после мержа main;
объём дифа; какие пункты чек-листа пройдены>

Не проверено
<что осталось без проверки: нагрузка, миграция на копии прод-данных, мобильный клиент
на реальном устройстве, сторонние интеграции, ручной сценарий в браузере>

Статус CI
<джоба: статус; локальные тесты на ветке; локальные тесты после мержа main>

Вердикт: МЕРЖИТЬ | МЕРЖИТЬ ПОСЛЕ <PR или условие> | НЕ МЕРЖИТЬ
```

Вердикт «МЕРЖИТЬ» без заполненных разделов «Проверено» и «Не проверено» не выносить: он читается как «код проверен целиком».
Мобильные и iOS-фиксы помечать явно: «требует проверки на реальном устройстве».

## 9. Публикация отчёта в PR

Результат ревью должен остаться в PR, а не только в сессии: иначе автор его не увидит, а следующее ревью начнётся с нуля.

- Спросить разрешение на публикацию, затем:
  - находки, привязанные к строкам дифа, — одним ревью с построчными комментариями:

    ```bash
    cat > review.json <<'JSON'
    {"commit_id":"<SHA головы>","event":"COMMENT","body":"<шапка отчёта>",
     "comments":[{"path":"app/Foo.php","line":42,"side":"RIGHT","body":"БЛОКЕР 1: ...\nСценарий: ..."}]}
    JSON
    gh api repos/{owner}/{repo}/pulls/<номер PR>/reviews -X POST --input review.json
    ```

  - находки вне дифа (раздел «Было до PR») и сам отчёт целиком — в тело ревью или отдельным комментарием: `gh pr comment <номер PR> --body-file <файл>`.
- Не ставить `APPROVE` и `REQUEST_CHANGES`: вердикт — текстом, решение о мерже за человеком.
- Повторное ревью редактирует свой прошлый комментарий, а не плодит новые:
  `gh api repos/{owner}/{repo}/issues/comments/<id> -X PATCH -F body=@<файл>` (`-F`, не `-f`: только `-F` читает значение из файла).
- В конце комментария — блок состояния, по нему следующее ревью поймёт, что уже проверено:

  ```
  <!-- mega-skills-review commit=<SHA головы> open=1,2 closed=3 scope=full|SHA..SHA -->
  ```

- Если публиковать не разрешили — оставить отчёт в сессии и сказать, что повторное ревью пойдёт с нуля.

## 10. Уборка

- Остановить поднятые контейнеры (`bin/test-worktree.sh down` или `docker compose -p <проект> down`).
- Удалить **временный** worktree, созданный в пункте 2: `git worktree remove <путь-в-temp>` (при незакоммиченных правках — `--force`), затем `git worktree prune`.
- Текущий worktree сессии не удалять.
