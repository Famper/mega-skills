# Фича в нескольких репозиториях

Фича: `$ARGUMENTS`

## Фаза 1. План (обязательно остановиться и показать)

Составить план и **дождаться одобрения пользователя** перед написанием кода:

- Список затрагиваемых репозиториев и изменений в каждом.
- Контракт API: эндпоинты, формы запросов и ответов, коды ошибок, права доступа.
- Миграции БД и конфигов.
- Порядок мержа и деплоя. По умолчанию: **backend → gateway → frontend**.
- Риски: проверить последние коммиты и открытые PR в каждом репозитории. Если репозиторий активно переписывается другим человеком — отметить это, чтобы пользователь согласовал архитектуру с владельцем до начала работы.
- Даты и время: явно указать формат (unix-timestamp, часовой пояс Москвы, если не сказано иное).

## Фаза 2. Реализация

- Отдельный git worktree на каждый репозиторий. Если задачи независимы — по субагенту на репозиторий.
- Перед тестами — скилл `preflight`.
- В каждом репозитории: тесты, падающие без изменения; зелёные линтер, статический анализ и тесты локально.
- PR в каждом репозитории. В описании: ссылки на соседние PR и условие мержа («мержить после backend#NNNN»).

## Фаза 3. Интеграция

- Поднять локальный стенд и пройти пользовательский сценарий в браузере, сделать скриншоты.
- Для каждого эндпоинта, который вызывает фронтенд, убедиться, что он существует в main или в PR бэкенда этой же фичи.
- Проверить данные, которые пишет фича: нет дублей, нет дат 1970, старое и новое значения различаются.

## Фаза 4. Выдача

1. Чеклист мержа по порядку со ссылками на PR.
2. Список smoke-тестов после деплоя.
3. После мержей — `git fetch && git log origin/main --oneline -20` в каждом репозитории и подтверждение, что все изменения на месте.
4. Ответ клиенту — по правилам скилла `customer-reply` (обычный текст, проверенное имя адресата).
